1
File Structure
How to package your addon as a ZIP archive

Every TurboFPS addon is a ZIP archive containing a single folder at its root. That folder holds all your addon files. The installer validates this structure before extraction — loose files at the ZIP root will cause immediate rejection.

Correct Structure
your_addon.zip
    └── my_addon_folder/
        ├── module.prop          ← Required — metadata
        ├── install.sh           ← Required — install / activate script
        ├── uninstall.sh         ← Recommended — cleanup script
        ├── status.sh            ← Optional — live status checker
        ├── changes.txt          ← Optional — changelog
        ├── webroot/             ← Optional — Web UI folder
        │       └── action.html    ← Web UI entry page
        └── banner.png           ← Optional — card background image
Incorrect Structure (Rejected)
your_addon.zip
    ├── module.prop    ← Files at root — no parent folder!
    ├── install.sh
    └── action.html
One Folder at Root
Your ZIP must open to show exactly one folder. Files placed directly at the root of the ZIP will cause installation to fail with no further error.
2
module.prop
The metadata file that identifies your addon to the installer

This is a plain-text key=value file that tells TurboFPS Pro everything about your addon. Every field is read, validated, and displayed in the addon card UI. Without a valid module.prop the installer will reject your addon.

Format
properties module.prop 
id=com.yourname.addonname
name=My Awesome Addon
version=1.0
versionCode=1
author=YourName
description=Short description of what this addon does
turbofps=true
Field Reference
Field Example Description Status
id com.you.addon Unique identifier in reverse domain format. Duplicate IDs are rejected or prompt an update dialog. Required
name My Addon Display name shown on the addon card. Required
version 1.0 Human-readable version string shown on the card. Required
versionCode 1 Integer used for update comparison. A higher number means a newer version and triggers an auto-update flow. Required
author YourName Creator name shown on the card. Required
description Optimizes CPU... Short description shown below the addon name on the card. Required
turbofps true Compatibility flag. Must be exactly true (lowercase). Addons without this are blocked immediately. Required
Update Flow
If an addon with the same id is already installed, the installer compares versionCode. A higher code replaces the old addon automatically. A same or lower code shows a "Already installed / up to date" message and skips installation.
3
Install Scripts
Runs when your addon is installed or its toggle is turned ON

When a user installs your addon or enables it via the toggle switch, TurboFPS Pro searches for and runs your install script. The installer checks for these filenames in priority order — all names are accepted case-insensitively.

Script Priority Order
1
customize.sh
Highest priority. Runs before all others. Use for complex setup logic.
2
install.sh
Standard install script. Most addons use this.
3
activate.sh
Alternative name for install logic.
4
run.sh
Another alternative name.
5
action.sh
Another alternative name.
6
service.sh
Another alternative name.
Case-Insensitive
The installer accepts install.sh, Install.sh, and INSTALL.SH equally. The script is also searched recursively inside subfolders.
Example install.sh
shell install.sh 
#!/system/bin/sh

ui_print "Installing My Addon..."
ui_print "Applying optimizations..."

# Always validate the path before writing
if [ ! -f "/sys/devices/system/cpu/cpu0/cpufreq/scaling_governor" ]; then
    ui_print "! CPU governor not available on this device"
    exit 1
fi

echo "performance" > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor

ui_print "Done! Addon is now active."
Available Helper Functions
FunctionDescription
ui_print "message" Prints a message to the live installer log shown to the user during installation.
set_perm 0 0 0755 /file Sets ownership and permissions on a specific file.
set_perm_recursive /dir 0 0 0755 0644 Sets permissions recursively on a directory.
$TURBOFPS_ADDON Environment variable automatically injected — full path to your extracted addon folder.
4
Uninstall Scripts
Runs when your addon is removed or its toggle is turned OFF

When a user uninstalls your addon or turns off the toggle, the installer looks for an uninstall script and runs it. Accepted filenames (searched in order):

1
customize.sh
Runs first — handles both install and uninstall directions.
2
uninstall.sh
Standard uninstall script.
3
deactivate.sh
Alternative name.
4
revert.sh
Alternative name.
5
reset.sh
Alternative name.
Example uninstall.sh
shell uninstall.sh 
#!/system/bin/sh

ui_print "Removing My Addon..."
ui_print "Reverting changes..."

# Restore the default value
echo "schedutil" > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor

ui_print "Uninstall complete. System restored."
Critical Rule — Always Revert
Every system change made during installation must be reversed during uninstallation. Failing to clean up can leave the device in an unstable state and will result in your addon being reported by users.
5
Status Checker
Optional — adds a real-time status button to your addon card

When you include a status.sh file in your addon folder, TurboFPS Pro automatically adds a Status button to your addon card. Tapping it runs the script and streams all output live to a log overlay — without requiring any additional setup from you.

How It Works
  • 1
    Add status.sh anywhere inside your addon folder (the installer finds it recursively).
  • 2
    When the user taps the Status button, TurboFPS runs the script via Shizuku privileged shell.
  • 3
    All output from echo and ui_print is streamed live to a scrollable log screen.
  • 4
    The log stays open until the user taps back — giving them time to read the full output.
Example status.sh
shell status.sh 
#!/system/bin/sh

echo "======================================="
echo "  My Addon - Status Check"
echo "======================================="

CURRENT=$(cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor 2>/dev/null)

if [ "$CURRENT" = "performance" ]; then
    echo "  Status  : ACTIVE"
    echo "  Governor: performance"
else
    echo "  Status  : INACTIVE"
    echo "  Governor: $CURRENT (expected: performance)"
fi

echo "  Device : $(getprop ro.product.manufacturer) $(getprop ro.product.model)"
echo "  Android: $(getprop ro.build.version.release)"
echo "======================================="
Tips for a Good Status Script
Always read the actual system values your addon changed — never fake output. Show ACTIVE / INACTIVE / PARTIAL clearly at the top. Include device info and Android version for easy debugging. Do NOT use emoji characters — they cause encoding errors on some devices.

Changelog
Optional — adds a version history button to your addon card

Including a changes.txt file enables a Changelog button on your addon card. Users tap it to see a scrollable bottom sheet with your version history. Highly recommended for any published addon.

Requirements
  • File name must be exactly changes.txt (case-sensitive on some devices)
  • Plain text only — no HTML or Markdown
  • Use UTF-8 encoding with Unix line endings (LF, not CRLF)
  • Do not use Windows-style CRLF line endings — they show as ^M characters
Recommended Format
text changes.txt 
======================================
 My Addon - Changelog
======================================

v2.0 (2026-03-01)
----------------
Added status.sh for real-time checks
Improved uninstall cleanup
Fixed crash on Android 14

v1.0 (2026-01-01)
----------------
Initial release

--------------------------------------
Author : YourName
======================================
7
Web UI Page
Optional — a full interactive HTML settings page inside your addon

You can include a full HTML page that opens as a settings/control panel for your addon. This lets you build interactive mode selectors, dashboards, sliders, and more — all with custom design — without any limitations on what you can create with HTML and JavaScript.

Folder Structure

Put your Web UI inside a webroot/ folder (or addon-ui/) inside your addon directory. TurboFPS searches these folder names automatically and serves files from them.

my_addon_folder/
    ├── module.prop
    ├── install.sh
    └── webroot/                   ← Web UI folder
            ├── action.html       ← Entry page (loaded first)
            ├── style.css
            ├── app.js
            └── icon.png          ← Images inside webroot load directly
Accepted Folder Names
TurboFPS accepts: webroot, addon-ui, Mod-UI, mod-ui, ui, www. If none of these exist, it recursively searches for any folder containing index.html or action.html.
Entry Page

The WebView loads action.html if it exists; otherwise it loads index.html. All files inside your webroot folder are served and accessible directly by filename — no paths needed.

WebView Capabilities
  • Full JavaScript enabled
  • DOM Storage enabled (localStorage, sessionStorage)
  • CSS animations, custom fonts, external CDN resources
  • File chooser / file picker supported
  • Download links handled automatically
  • Access outside your webroot folder is blocked for security

Banner Image
Optional — visual branding on your addon card

Include one image file to add a custom background to your addon card in TurboFPS Pro. The installer automatically finds the first image in your addon folder and uses it.

PropertyRecommended Value
Supported formats .png, .jpg, .jpeg
Recommended size 800 × 600 px or any landscape ratio
Display opacity ~36% — shown as a subtle background behind card content
Max file size Under 500 KB recommended for faster loading
Filename Any name — installer picks the first image found (e.g. banner.png)
Design Tip
Since the image is shown at ~36% opacity over the card surface, dark or desaturated images with subtle gradients work best. Avoid busy or high-contrast images that make text hard to read.
9
JavaScript Bridge API
Run shell commands and interact with the app from your Web UI

When your Web UI page opens, TurboFPS injects a JavaScript bridge object called TurboAndroid. You can call its methods from any JavaScript code inside your webroot to execute shell commands, show toasts, read addon info, and control the UI chrome.

KernelSU Compatibility
TurboFPS also registers a ksu alias pointing to the same bridge. Community addons built for KernelSU will work without modification.
Available Methods
TurboAndroid
.exec(cmd)
Execute a shell command synchronously and get the output as a string.
javascript
// Synchronous — returns output directly
var output = TurboAndroid.exec("getprop ro.product.model");
console.log(output);
TurboAndroid
.exec(cmd, callback)
Execute a shell command asynchronously. Calls callback(exitCode, stdout, stderr) when done.
javascript
// Async with callback
TurboAndroid.exec(
    "cat /proc/cpuinfo",
    function(exitCode, stdout, stderr) {
        if (exitCode === 0) {
            document.getElementById("output").textContent = stdout;
        } else {
            console.error(stderr);
        }
    }
);
TurboAndroid
.exec(cmd, options, callback)
Async with extra options — custom working directory and extra environment variables.
javascript
TurboAndroid.exec(
    "./my_script.sh",
    JSON.stringify({
        cwd: "/data/local/tmp/turbofps/plugins/my_addon",
        env: { "MY_MODE": "turbo" }
    }),
    function(code, out, err) { console.log(out); }
);
TurboAndroid
.toast(message)
Show an Android toast notification.
javascript
TurboAndroid.toast("Settings saved!");
TurboAndroid
.moduleInfo()
Returns addon metadata as a JSON string — id, name, version, and moduleDir path.
javascript
var info = JSON.parse(TurboAndroid.moduleInfo());
// { id: "com.you.addon", name: "My Addon", version: "1.0", moduleDir: "/data/..." }
console.log(info.name, info.version);
TurboAndroid
.getImageBase64(filename)
Load an image from the addon root (outside webroot) as a base64 data URI. Images inside webroot load directly with <img src="file.png"> — use this only for images in the addon root.
javascript
// Only for images OUTSIDE webroot (in addon root folder)
var src = TurboAndroid.getImageBase64("banner.png");
document.getElementById("bg").src = src;

// Images INSIDE webroot — just reference directly
// <img src="icon.png"> works without any bridge call
TurboAndroid
.fullScreen(enable)
Hide or show system bars (status + navigation). Pass true to go fullscreen, false to restore.
javascript
TurboAndroid.fullScreen(true);   // Hide system bars
TurboAndroid.fullScreen(false);  // Restore system bars
TurboAndroid
.setSystemBarsColor(color, darkIcons)
Set the color of both status bar and navigation bar. Use darkIcons: true for light backgrounds (dark icons), false for dark backgrounds (light icons).
javascript
// Dark background UI — use light icons
TurboAndroid.setSystemBarsColor("#0f0f0f", false);

// Light background UI — use dark icons
TurboAndroid.setSystemBarsColor("#FFFFFF", true);
Environment Variables in Scripts

These variables are automatically available in every shell command run through the bridge:

$TURBOFPS_MODULE_DIR
Full path to your addon's folder. Use this to reference files inside your addon.
$TURBOFPS_ADDON
Same as MODULE_DIR — also injected for install/uninstall scripts.
$TURBOFPS_PLUGINS
Path to the plugins directory where all addons are stored.
$PATH
Extended automatically to include your addon's system/bin folder (if it exists), so bundled binaries are found first.
Safety Filter
All commands sent via .exec() pass through a built-in safety filter. Destructive commands (filesystem wipes, fork bombs, remote code execution via wget/curl, block device writes, etc.) are automatically blocked and logged. This protects users from malicious addons.

Batch Installer
Distribute multiple addons in one ZIP

TurboFPS Pro includes a Batch Installer that lets you package multiple addons into a single master ZIP. Users select it once and all compatible addons inside are installed in sequence — with live progress shown for each one.

Batch ZIP Structure
my_addon_pack.zip  ← Master ZIP (user selects this)
cpu_tweaks.zip
gpu_optimizer.zip
network_boost.zip
Rules
  • Each inner ZIP must be a valid TurboFPS addon with turbofps=true
  • Inner ZIPs must be placed directly at the root of the master ZIP (no subfolders)
  • Already-installed addons with the same id are skipped (not reinstalled)
  • Addons with a higher versionCode than the installed one are updated automatically
  • Inner ZIPs missing turbofps=true are silently skipped (not counted as failures)
How to Create a Batch ZIP
Select all your addon ZIPs (e.g. cpu_tweaks.zip, gpu_optimizer.zip) and add them together into a new ZIP. Do not wrap them in a subfolder — they must be at the root of the master ZIP.

Safety & Best Practices
Writing reliable, safe, and compatible addons
Shell Script Rules
  • Start every script with #!/system/bin/sh
  • Use POSIX-compliant syntax only — avoid bash-specific features
  • Use Unix line endings (LF) — Windows CRLF causes silent failures
  • Use absolute paths for all file operations
  • Always check if a file/path exists before writing to it
  • Never use emoji in shell scripts — encoding errors on some devices
  • Never use destructive commands without validating paths first
Error Handling Pattern
shell install.sh — error handling 
#!/system/bin/sh

# 1. Check path before writing
if [ ! -f "/sys/devices/system/cpu/cpu0/cpufreq/scaling_governor" ]; then
    ui_print "! CPU governor not available on this device"
    exit 1
fi

# 2. Handle write failure with ||
echo "performance" > /sys/.../scaling_governor || {
    ui_print "! Failed to apply setting"
    exit 1
}

# 3. Confirm success
VERIFY=$(cat /sys/.../scaling_governor)
if [ "$VERIFY" = "performance" ]; then
    ui_print "Applied successfully"
else
    ui_print "! Verification failed"
fi
Good vs. Bad Practices
GOOD 
# Check before writing
if [ -f "$path" ]; then
    echo "value" > "$path"
fi

# Revert on uninstall
echo "schedutil" > "$path"

# Use ui_print for user output
ui_print "Setting applied"
BAD 
# Write blindly without check
echo "value" > "$path"

# No uninstall / cleanup
(no uninstall.sh)

# Emoji in shell script
echo "Done! ✅"
Test Before Publishing
Always test your addon on a non-production device before sharing it. Install it, verify it works, toggle it off, verify it uninstalls cleanly, and check the status.sh output. A addon that leaves broken state will be reported by users.

Publishing Checklist
Everything to verify before you release your addon
  • 1
    ZIP structure — your ZIP opens to a single folder. No files at root level.
  • 2
    module.prop — all required fields present, turbofps=true set, id is unique and in reverse domain format.
  • 3
    Install script — uses #!/system/bin/sh, LF line endings, checks paths before writing, prints clear messages via ui_print.
  • 4
    Uninstall script — reverts every change made by install.sh. Tested that device returns to normal state after toggle-off.
  • 5
    No emoji in any shell script file.
  • 6
    Status script (if included) — reads real system values, output is clear and human-readable, exits with code 0.
  • 7
    changes.txt (if included) — UTF-8 encoding, LF line endings, file name is exactly changes.txt.
  • 8
    Web UI (if included) — inside webroot/ folder, entry page is action.html or index.html, tested in-app.
  • 9
    Banner image (if included) — under 500 KB, landscape ratio, no sensitive branding.
  • 10
    Full install-toggle-uninstall cycle tested on a real device without issues.
